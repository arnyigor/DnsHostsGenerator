# Control D — разведка API для импорта hosts-правил

> Итог последующей проверки: необходимый функционал требует платного тарифа
> Full Control. В бесплатный сценарий не включаем; реальный импорт правил не проверен,
> экспериментальный код Control D не входит в коммит с проверкой DNS.
> Ниже — первоначальная разведка. Актуальный итог:
> [DNS_ALTERNATIVES_VERIFIED.md](DNS_ALTERNATIVES_VERIFIED.md).

Дата: 28.10.2026. Источник: официальные доки (`docs.controld.com`, у них есть md-версии страниц
и индекс `llms.txt`) + живые запросы к `api.controld.com` с этой сети.

## 1. Доступность с этой сети (проверено)

| Хост | Результат |
|---|---|
| `controld.com` | HTTP 200 |
| `docs.controld.com` | HTTP 200 (302 на /overview) |
| `api.controld.com` | отвечает: неизвестный путь → HTTP 400, с неверным токеном → JSON `{"success":false,"error":{"code":40001,"message":"Invalid session..."}}` |
| `doh.adguard-dns.com`, `api.adguard.com` | недоступны (для сравнения) |
| `api.nextdns.io` | недоступен (TLS reset/timeout) |
| DoT `p1.dns.controld.com:853` | TLS-хендшейк проходит, ответ приходит |

Вывод: Control D с этой сети **доступен целиком** — и API, и резолверы.

## 2. Аутентификация

- Заголовок: `Authorization: Bearer <token>`.
- Токен создаётся в дашборде: `controld.com/dashboard/api` → «+» → имя → уровень прав.
- Уровни: **Read** (только чтение) и **Write** (чтение + запись). Нам нужен Write.
- Опционально можно ограничить токен списком Allowed IPs.
- Формат ошибок: `{"success": false, "error": {"code": 40001, "message": "..."}}` — разбирать надо
  и HTTP-код, и `error.code`.

## 3. Профили

- `GET /profiles` — список профилей аккаунта, у каждого есть `PK` (пример из доков: `abcd123`).
  `PK` нужен во всех изменяющих вызовах.
- Для org-аккаунтов можно «имперсонировать» суб-организацию заголовком `X-Force-Org-Id`.
- Отдельного API для **создания аккаунта** нет: нужен зарегистрированный аккаунт и токен.
  Это принципиальное отличие от NextDNS, где приложение создавало анонимный временный аккаунт.

## 4. Custom Rules — это и есть «hosts в облаке»

Из документации (`/docs/custom-rules`):

> Custom Rules are basically a hosts file, with wildcard support. Block, redirect or spoof any
> domain to any IP.

- До **10 000** правил на профиль.
- При пересечении правил побеждает **самое специфичное** (поддомен перекрывает домен).
- Действия: `BLOCK` (0), `BYPASS` (1), `SPOOF` (2), `REDIRECT` (3) — числовые коды.
  - **SPOOF (2)** — вернуть заданный IPv4/hostname (наш случай: `IP домен`).
  - REDIRECT (3) — гнать через прокси-локацию (не наш случай).

### Создание правил: `POST /profiles/{profile_id}/rules`

`Content-Type: application/x-www-form-urlencoded`, поля:

| Поле | Смысл |
|---|---|
| `do` | тип правила: 0 BLOCK, 1 BYPASS, **2 SPOOF**, 3 REDIRECT |
| `status` | 1 — включено (0 — выключено) |
| `via` | для SPOOF — IPv4 или hostname; для REDIRECT — id прокси |
| `via_v6` | для SPOOF — IPv6 (AAAA) |
| `group` | id папки (иначе корень) |
| `comment` | до 64 символов |
| **`hostnames[]`** | **массив доменов — один запрос создаёт правило сразу для пачки** |

Ответ — 200. Это ключевое: batch есть «из коробки», как `hostnames[]`, а не по одному запросу
на домен (у NextDNS пришлось делать пачки с задержкой из-за rate limit 60/мин).

## 5. Как телефон начнёт это использовать

Правила применяются не к «аккаунту», а к **Endpoint** (резолверу) внутри профиля:
из дашборда выдаются DoH / DoT / DoQ (и, опционально, legacy IPv4/IPv6).

- Формат DoT-хоста, который мы проверили живьём: `p1.dns.controld.com:853` — TLS проходит,
  ответ приходит (у бесплатного профиля `p1` ответ был пустой для gemini/chatgpt, т.е. это
  просто «голый» резолвер без наших правил).
- Для Android это ложится на «Частный DNS»: hostname вида `<endpoint-id>.dns.controld.com`
  (конкретный id выдаётся в дашборде при создании Endpoint).

## 6. Что это значит для нашего приложения

**Хорошая новость:** модель данных совпадает с нашими hosts почти один-в-один.

```
наш hosts:   103.137.248.179 chatgpt.com
ControlD:    POST /profiles/{pk}/rules  do=2  status=1  via=103.137.248.179  hostnames[]=chatgpt.com
```

**Плохая новость:** нет анонимного создания аккаунта — пользователь должен один раз
зарегистрироваться и вставить токен. Полностью «в один клик», как с NextDNS, не получится.

**План реализации (если делаем):**
1. `ControlDClient` рядом с `NextDnsClient`: `GET /profiles` (валидация токена + выбор профиля),
   `POST /profiles/{pk}/rules` пачками по `hostnames[]` (например, 200 доменов на запрос),
   разбор ошибок `{"success":false,"error":{...}}`.
2. Режимы импорта: «добавить» (по умолчанию) и «заменить» (нужен список/удаление существующих
   правил — в API есть CRUD правил, точный путь DELETE надо сверить по reference-странице).
3. UI: в блоке импорта — выбор «NextDNS / ControlD», поле токена, выбор профиля из списка,
   кнопка «Залить правила» + счётчик (N добавлено, M ошибок).
4. Токен хранить локально (DataStore/настройки), не логировать; при 401 — просить новый.
5. Тесты: фейковый `Call.Factory` (как в `NextDnsClient`) + юнит-тесты на парсинг ошибок;
   живой тест — только для чтения профилей.

## 7. Что ещё надо уточнить перед кодированием

- Лимиты бесплатного тарифа: сколько профилей/правил и доступен ли API-токен на free
  (доки говорят про 10 000 правил, но не привязывают к плану — на публичной странице цен этого нет).
- Точный путь и семантика удаления/замены правил (`DELETE`/`PUT` по rule id) — есть в reference,
  но я его не выкачивал.
- Rate limit API (в доках не встретился; у NextDNS было 60/мин).
- Принимает ли SPOOF hostname (CNAME) — нам достаточно IPv4, но лучше знать.

## 8. Итог

Control D закрывает главную проблему: **API доступен с этой сети**, правила — это хостовый формат
с wildcard и batch-созданием. Единственный непреодолимый автоматикой шаг — регистрация аккаунта
и выпуск токена: один раз вручную, дальше импорт можно делать из приложения.
