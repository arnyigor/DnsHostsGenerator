## 1. Что предлагает пост

Пайплайн «свой DNS-профиль вместо чужого резолвера»:

```
hosts-списки сообщества (прокси-IP)  ──►  DnsConf (скрипт)
                                            │  парсит списки, дедуп, wildcard-компрессия
                                            ▼
NextDNS / Cloudflare API  ──►  rewrite-правила в ЛИЧНОМ профиле
                                            ▲
GitHub Actions (ночью)  ────────────────────┘
```

- Точка входа — `https://dns-conf-ui.vercel.app`: GitHub-логин + ID/токен провайдера, одна кнопка.
- UI создаёт форк `DnsConf`, пишет secrets/env, запускает Action; скрипт тянет списки, заливает правила
  в профиль, повторяет для N профилей, обновляется каждую ночь.
- NextDNS vs Cloudflare: в РФ рекомендуется **NextDNS** (300k запросов/мес, автопроксирование
  поддоменов, API 60 req/min → первая настройка ~20 мин); Cloudflare — 100k/день, нет пресетов
  блокировки рекламы, жёсткая привязка IPv4-адреса DNS, нужна карта/PayPal.
- Ключевая мысль автора: готовые Comss/Xbox DNS получают **весь** DNS-трафик пользователя и не дают
  гарантий; поэтому — свой профиль, куда попадают только нужные домены.

## 2. Чем наш пайплайн отличается

| Аспект | Пост (DnsConf → NextDNS/Cloudflare) | DnsHostsGenerator |
|---|---|---|
| Откуда берутся IP | готовые hosts-списки сообщества (чужие SNI-прокси) | ответ выбранного DNS-пресета **в момент генерации** |
| Куда применяется | rewrite-правила в личном DNS-профиле | hosts-файл на устройстве (или API-импорт в NextDNS) |
| Поддомены | NextDNS проксирует поддомены сам; Cloudflare — `*.domain` | только точные имена из списка; wildcard невозможен |
| Обновление | GitHub Actions каждую ночь, без участия пользователя | вручную, повторной генерацией |
| Фильтрация рекламы/трекеров | пресеты NextDNS / oisd | нет |
| Кто видит домены | только свой профиль у выбранного провайдера | DNS-провайдер пресета + владелец его прокси |
| Отказоустойчивость | профиль живёт независимо от устройства | hosts — одна точка: умер IP → править файл заново |
| Проверка «IP рабочий?» | нет (заливает то, что в списке) | нет (см. §4) |

Вывод: архитектурно наше приложение — это **генератор снимка** (snapshot) hosts, а пост описывает
**непрерывно обновляемый профиль**. Основная разница не в «правильных DNS», а в том, что у нас
между DNS-ответом и файлом нет проверки, что полученный IP вообще обслуживает домен.

## 3. Что показали живые измерения (10 пресетов × 4 домена)

Проверка: A-запрос по DoT (853, как в `DnsJavaResolver`), затем TLS-хендшейк на 443 к каждому
полученному IP с SNI проверяемого домена. «USABLE» = IP отдаёт валидный сертификат на этот домен.

| Пресет | DoT | chatgpt.com | gemini.google.com | api.anthropic.com | claude.ai | Итог |

| dns.astracat.ru | **ошибка TLS** (hostname mismatch) | UDP-фолбэк → 217.60.179.6 ✅ | ✅ (тот же IP) | — | — | работает только через UDP:53 |
| dns.comss.one (рекомендуемый) | ок | 80.74.30.162, 132.243.113.26 ✅✅ | 199.189.249.126 ✅ | 80.74.30.162, 132.243.113.26 ✅✅ | ✅ | **работает** |

Что из этого следует:

1. **«Не те DNS-серверы» — частично верно.** Из 10 пресетов рабочие IP дают 3 (`bezmezhau`, `comss.one`,
   `zapret.moe`) плюс `astracat` через UDP-фолбэк. `geohide`, `pro.shecan.ir`, `malw.link` отвечают по
   DoT, но отдают **недостижимые из этой сети** адреса — приложение молча запишет их в hosts.
2. **Рекомендуемый comss.one работает, но отдаёт два IP, один из которых — 80.74.30.162.** Тот же адрес
   возвращает и DNS нашего ISP для `chatgpt.com` и `api.anthropic.com`: это общий SNI-прокси, через
   который ходит провайдер. Никакой проблемы доступа это не создаёт (TLS валиден), но именно про такие
   «чужие прокси» предупреждает пост.
3. **`free.shecan.ir` для OpenAI/Gemini отдаёт настоящие Cloudflare/Google IP**, а не прокси: для
   `api.anthropic.com`/`claude.ai` настоящий `160.79.104.10` вообще не открывается по TCP. То есть
   «DNS ответил» ≠ «домен доступен» — и это главный измеримый разрыв.

## 4. Почему «не всё работает» — конкретные места в коде

| # | Место | Что происходит | Наблюдаемый эффект |
|---|---|---|---|
| 1 | `domain/Models.kt:89` + `generator/HostsGenerator.kt:132` — `IpSelectionStrategy.First`, `ip = primaryIps.first()` | берётся **первый** IP из ответа, без проверки живости | у `malw.link` в hosts попадает 179.254.166.174, который вообще не отвечает |
| 2 | `generator/HostsGenerator.kt:115-116` — `hasCommonIp = checkIps.any { it in primaryIps }` | **любое** пересечение с check-DNS выбрасывает домен в `#forwarded`, хотя рядом мог быть рабочий IP (`comss` = ISP-адрес + свой) | на сетях с DNS-прокси/перехватом домены пропадают из результата целиком |
| 3 | `domain/Models.kt:17` — `checkDns = "8.8.8.8"` (+ `checkDotHost = "dns.google"`) | проверка идёт через Google DoT; если он недоступен, `checkIps` пуст | `checkIps.isEmpty()` → ветка `Forwarded` не срабатывает, детект перехвата **молча** отключается |
| 4 | `domain/Models.kt:92` — `timeoutMillis = 5_000` | у `geohide` один прогон дал ответ за 28 с, другой уложился в 6 с | домены уходят в `Unresolved` без объяснения причины |
| 5 | `data/BuiltInDnsPresets.kt` | пресеты не проверяются на живость и на пригодность IP | в UI выглядят равнозначными; фактически 4 из 10 нерабочие |

Пункты 1 и 2 — не «мелкие баги», а отсутствие инварианта: **IP из DNS обязан подтверждаться TLS-хендшейком
с SNI домена**, иначе hosts-строка бесполезна. Проверка дешёвая (один TCP+TLS на IP, ~300–600 мс),
и именно она отличает «работающий» пресет от «отвечающего по DoT».

## 5. Что делать, по приоритету

1. **P1. Валидация IP перед записью в hosts** (`HostsGenerator`): TLS-хендшейк с SNI домена и проверкой
   сертификата; невалидные/недостижимые IP отбрасывать, домен → `Unresolved`/новый статус «IP не обслуживает
   домен». Это закрывает malw/pro.shecan/geohide-класс ошибок.
2. **P1. Выбор стратегии IP**: вместо `First` — «первый валидный» (после TLS-проверки), а при равенстве
   предпочитать IP, которого нет в ответе check-DNS (то есть реально прокси-адрес, а не форвард).
3. **P2. Ослабить `hasCommonIp`**: считать `#forwarded` только когда **все** primary-IP входят в check-набор;
   если есть непересекающийся IP — использовать его. И предупреждать, когда `checkIps` пуст (проверка не выполнена),
   а не молча писать «всё хорошо».
4. **P2. Привести пресеты в соответствие с фактами**: `geohide`, `pro.shecan.ir`, `malw.link` — либо
   `enabledByDefault = false` + `disabledReason` (как уже сделано для `xbox-dns.ru`), либо per-preset timeout.
5. **P3. Per-preset timeout** (или 10 с вместо 5 с) и ретрай: `geohide` физически не укладывается в 5 с.
6. **P3. Кнопка «проверить пресеты»** — прогон 1–2 доменов по всем пресетам с вердиктом
   «DoT / IP / TLS», чтобы список не расходился с реальностью (эти данные получены именно такой пробой).
7. **P4. Закрыть разрыв с постом по поддоменам**: hosts не умеет wildcard. Либо экспорт в
   NextDNS/Cloudflare-rewrite с `domain.com`/`*.domain.com` (у приложения уже есть API-импорт в NextDNS),
   либо явная пометка в UI, что поддомены нужно вносить отдельно.

## 6. Что не проверено

- Проверялся TLS-уровень (сертификат на домен), а не полная сессия: DPI может рвать уже после хендшейка.
  Для `free.shecan.ir` (реальные Cloudflare-IP) это существенно — «TLS ок» там не гарантирует загрузку.
- Измерения сделаны с одного ISP/одной сети 23.10.2026; у другого оператора картина пресетов другая.
- Утверждения поста про сбор данных Xbox DNS и про «100 % вайбкод» DnsConfUI не проверялись.
- Ветка «NextDNS/Cloudflare-профиль + DnsConf» в приложении не запускалась: API-импорт в NextDNS есть,
  но совместимость с форматом DnsConf (`domain.com` без поддоменов) не тестировалась.
